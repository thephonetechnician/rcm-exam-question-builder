# Class administration upgrade — 14 November 2026

This replaces the routine three-tab manual registration workflow. The administrator
chooses a class once, then adds courses and students through the portal. Lecturers
still submit without login and lock results with a PIN.

## Install on staging first

1. After reviewing/committing/pushing the local changes and pulling into Codespaces,
   replace the staging Apps Script contents of `09_ScoreService.gs` and
   `10_ScoreSetup.gs`. Add the new `11_ClassManagement.gs`. Keep the existing
   `score.` router branch in `02_WebApp.gs`; no new branch is needed.
2. Create a temporary Script file containing:

   ```javascript
   function updateClassTables() {
     setupScoreMvp_();
   }
   ```

   Run `updateClassTables`, confirm successful execution, then delete only that
   temporary file before deployment. Setup adds `ScoreClasses`,
   `ScoreClassEnrolments` and `ScoreAdditions`, and recognises classes from existing
   course metadata. It never deletes/replaces existing scores or history.
3. Update the existing staging deployment to a **New version**, keeping its URL.
   Hard-refresh the frontend. Use the same administrator key and Script Properties;
   do not reset the key, hash, salt, spreadsheet ID or frontend origin.

## Administrator workflow

1. Sign in at `score-admin.html`. Create or choose an active-session class using
   Programme and Level/Set. The session comes from Config `CURRENT_SESSION`.
2. Choose **Manage courses** and a semester. Download its Excel template, fill in
   CourseCode, Title and Units, upload the file, preview and confirm. Or open
   **add one course directly** to register a single course without a file.
3. Choose **Manage students**. Download its template, fill in Name, MatNo and optional
   AdmissionNo, upload, preview and confirm. A student without MatNo needs an
   AdmissionNo for reliable duplicate detection. Single-student entry is also available.

The selected class/session/semester is attached automatically. References are
generated by the server. There are no StudentRef/CourseRef columns to fill and
no per-course regular registration rows. Every active class member appears in
each regular course for that class/session, across its semesters.

Templates are class-specific. A hidden context sheet prevents accidentally uploading
one class/semester's template into another. Input headings stay on row 1. Preserve
the Courses or Students tab name. Do not add formulas. Matric/admission columns are
formatted as text to preserve leading zeros. Excel `.xlsx` and comma-separated CSV
are supported; `.xls` must first be saved as `.xlsx`. Limits: 1,000 rows and 3 MB per
upload. Course units must be greater than 0 and at most 30.

The older preparation workbook can be read by the new upload controls when its
selected Courses/Students tab contains only the currently selected class (and,
for courses, the selected semester). Existing context columns are checked. Split
a multi-class workbook or use the new class-specific templates. Its Registrations
tab is no longer needed for routine class enrolment. Do not use the old editor-only
`importScoreTemplate_` for this new workflow.

## What preview and confirm mean

- New records are added. Exact duplicates are skipped, including repeated rows.
- Different existing names/identifiers/course titles/units are conflicts; the portal
  will not silently overwrite them. All conflicts block the batch until corrected.
- Confirm rechecks the data under the server lock. If relevant records changed since
  preview, preview again. Interrupted appends can also be re-previewed: already-written
  student masters are reused and missing class enrolments are added without duplication.
- Students have stable internal references plus separate session/class enrolments.
  An exact existing identity may be enrolled in another session/class without changing
  the original master record. Historical sessions are read-only through this interface.
- Config session management and changing existing identities are not part of this
  first-release screen. Review such conflicts deliberately with the owner.

## Lecturer additions

The open score sheet has **Add student**. A name, matric number, registration type
(Regular, Carry-over or Additional) and reason are required. The lecturer can remove
an added row before submission; registered roster rows cannot be removed here.
Both client and server check duplicate matric numbers, and the server rejects a
conflict with an existing student identity or an inactive student.

Added students are included immediately, visibly marked **Lecturer added**, and
listed with their reasons in the final preview. Server records capture the typed
lecturer name and submission time; this name is not an authenticated identity.
The entire submitted sheet locks as before. Admin history exposes the addition
details for review; Excel includes source/type/reason columns and PDF flags names.
These rows do not silently enter the permanent class register. The admin may
register the verified student through Manage students for future course rosters.

## Preserve existing results

Old snapshots and archive events remain unchanged. New class students affect only
unsubmitted/reopened score entry; they do not rewrite a locked score sheet or its
downloads. Existing individual ScoreRegistrations are still honoured and deduplicated
against the class roster. Legacy registrations are not automatically promoted to
session/class membership, since some may be carry-over exceptions. Re-import the
class list to create proper class enrolments.
